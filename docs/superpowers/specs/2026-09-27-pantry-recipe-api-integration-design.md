# 팬트리·레시피 API 연동 설계

## 목적

첨부된 Pantry/Recipe OpenAPI 명세에 맞춰 목업 중심 화면을 실제 API 데이터에 연결한다. 이미 성공한 팬트리 및 레시피 목록 조회 흐름은 보존하고, 특히 연결되지 않은 레시피 상세 조회와 스크랩 등 나머지 지원 기능을 실제 서버 상태와 일치시킨다.

## 현재 상태와 범위

- 팬트리 목록·등록·수정·삭제 API 클라이언트와 화면 모델 매퍼가 존재한다. 팬트리 조회가 실제 데이터를 보여주는 흐름을 유지하고, 폼 및 목록의 mutation이 서버 응답/오류와 일치하는지 점검한다.
- 레시피 목록 API는 페이지 응답(`content`, `totalElements`, `totalPages`)을 반환한다. 검색은 `/api/recipes/search`, 팬트리 재료 후보는 `/api/recipes/filter-ingredients`를 사용한다. 화면의 mock fallback은 API 실패나 데이터 미도착을 정상 콘텐츠처럼 보이게 하므로 제거한다.
- 레시피 상세 API와 조회 훅은 존재하지만 상세 화면은 고정된 목업 재료·조리 단계로 렌더링한다. 응답 DTO를 화면 모델로 매핑해 상세 조회를 연결한다.
- 스크랩 추가/해제 API와 조리 완료 API 클라이언트는 존재하지만, 스크랩 화면 상태는 로컬 저장소에 의존한다. 서버 스크랩 목록 조회를 추가해 상세/목록/마이페이지 스크랩 상태가 서버 기준으로 일치하도록 한다.
- 요청은 공통 HTTP 클라이언트와 기존 인증 토큰 흐름을 사용한다. API 서버 주소는 기존 `NEXT_PUBLIC_API_BASE_URL` 설정을 이용하며 명세의 `localhost:8082`를 코드에 고정하지 않는다.

이번 범위는 명세에 실제로 존재하는 기능만 서버 연동한다: 팬트리 목록 검색·필터·정렬/CRUD, 페이지네이션 레시피 목록·검색, 팬트리 재료 필터, 레시피 상세/팬트리 매칭/상품 매칭, 스크랩 목록·등록·해제, 선택한 팬트리 항목 정리를 포함한 조리 완료. 기존 UI 디자인과 라우트는 유지한다.

## 명세상 미지원 기능

다음 기능은 이 OpenAPI에 엔드포인트나 데이터가 정의되어 있지 않으므로 가짜 서버 연동 또는 성공처럼 보이는 로컬 동작을 추가하지 않는다.

- 영수증 OCR 및 이미지 업로드/스토리지 URL 발급
- 레시피 분류 레일의 후기 수·스크랩 순위·공유 순위 산출 (목록 응답에는 해당 집계/분류 값이 없음)
- 레시피 상세 API에 없는 재료 수량·추가 팁 등 보강 정보

미지원 항목이 현재 화면에 노출되는 경우 실제 정보인 것처럼 목업을 섞지 않는다. 조회 API 결과로 구성할 수 있는 화면은 실제 응답만 표시한다. 2026-09-29에 추가된 Pantry/Recipe OpenAPI는 g 단위 필요 재료의 상품 매칭을 `GET /api/recipes/{recipeId}/product-match`로 정의한다. 다른 단위 또는 필요량이 없는 재료는 `UNSUPPORTED`일 수 있다.

## 구조 및 데이터 흐름

- `entities/pantry/api`: 기존 DTO, 요청 함수, 매퍼를 OpenAPI와 대조한다. 화면은 Query 훅으로 목록을 읽고 mutation 성공 후 팬트리 query cache를 무효화한다.
- `entities/recipe/api`: 페이지 목록·검색·필터 후보·팬트리 매칭·상세 조회, 스크랩 목록 Query, 조리 완료 mutation과 cache 갱신을 제공한다. 목록/상세/스크랩은 동일한 recipe ID와 UI 모델을 사용한다.
- `views/pantry` 및 `views/recipe`: 기존 UI 컴포넌트는 유지하고 loading/empty/error/content 상태를 서버 query 상태에서 결정한다. API 실패 시 mock fallback을 하지 않는다.
- `src/shared/api/http-client.ts`: 인증/공통 응답 envelope 처리를 재사용한다. 공개 레시피 조회와 인증이 필요한 스크랩/팬트리 기능의 401 동작을 확인한다.

의존 방향은 `views → entities/api → shared/api`를 유지하며, 페이지 컴포넌트에서 `fetch`를 직접 호출하지 않는다.

## 화면 및 상호작용 동작

- 팬트리 목록, 등록, 수정, 삭제는 서버 값을 기준으로 표시한다. 등록 이미지가 없으면 기존 기본 썸네일을 사용한다. 로컬 `blob:` URL은 업로드 API가 없으므로 영구 이미지로 서버에 전달하지 않는다.
- 레시피 목록 및 상세 로딩은 별도 상태로 표시한다. API 오류는 기존 공통 시스템 오류 화면과 재시도를 사용하며 목업 목록/상세를 성공 화면처럼 표시하지 않는다.
- 레시피 상세는 `RecipeDetailResponseDto`의 제목, 설명, 조리시간, 인분, 난이도, 썸네일, 재료, 단계 순서를 사용한다. 응답이 없는 상세 ID는 서버 오류 상태로 처리한다.
- 스크랩 mutation 성공 후 상세 아이콘, 레시피 목록 아이콘, `/mypage/scraps` 목록이 query cache로 동기화된다. 서버 실패 시 성공 상태로 남기지 않고 오류를 표시한다.
- 조리 완료는 `GET /api/recipes/{recipeId}/pantry-match`로 조회한 실제 `pantryItemId`를 사용한다. 사용자가 선택한 항목만 `POST /api/recipes/{recipeId}/cook-complete` body에 보내며 서버가 이력 기록과 팬트리 삭제를 한 트랜잭션으로 처리한다. 아무 항목도 선택하지 않으면 body를 생략해 기록만 남긴다.
- 팬트리 API 400/401/404, 레시피 상세·스크랩 추가 404, 인증이 필요한 스크랩·조리 완료의 401은 공통 API 오류 정보를 활용해 입력 오류, 로그인 필요, 항목 없음 상태로 처리한다. 공개 레시피 목록·상세 조회는 첨부 명세상 인증이 필요하지 않다.

## 검증

- DTO 매퍼 테스트: nullable 이미지, enum 라벨, 숫자 ID 변환, 재료 및 조리 단계 정렬.
- 요청 계약 테스트: 경로, query parameters, HTTP method, request body, Bearer 인증, 공통 응답 `data` unwrap.
- Query/mutation 테스트: 성공 시 캐시 갱신, 실패 시 낙관적 성공 상태가 남지 않는지.
- 화면 테스트: 로딩/빈 결과/오류·재시도/정상 결과, 목업 fallback 미사용, 서버 응답이 카드/상세에 표시되는지.
- 관련 기존 전체 테스트, `npm run check`, `NEXT_PUBLIC_API_BASE_URL`을 설정한 production build를 실행한다.

## 백엔드 연동 전제 및 합동 확인

- 명세의 개발 서버 `http://localhost:8082`는 배포 코드에 하드코딩하지 않고 환경별 API base URL 및 기존 Gateway 경로로 확인한다.
- 팬트리/스크랩 API는 로그인 access token 필요. 테스트 계정과 유효한 JWT를 준비한다.
- API 응답의 `data` envelope, 팬트리 날짜·보관 타입·등록 타입 enum, 레시피 nullable 이미지/실제 조리 순서, 에러 코드가 첨부 명세와 일치하는지 확인한다.
- 서버에 이미지 업로드와 레시피 랭킹 지표가 준비되면 그 계약을 별도 범위로 추가한다.
