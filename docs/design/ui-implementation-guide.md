# UI 구현 가이드

## 목적

PantryMate의 와이어프레임과 확정 UI를 구현할 때 화면마다 다른 기준을 만들지 않도록 돕는 실무 가이드입니다. 이 문서는 레이아웃, 공용 패턴, 상태, 접근성, 검수의 적용 방법을 다룹니다.

색상, 간격, 반경, 타이포그래피의 원본 값은 [디자인 시스템](./design-system.md)을 기준으로 합니다. 값이 충돌하면 디자인 시스템과 Figma를 우선하고, 이 문서는 구현 방식을 안내합니다.

## 적용 순서

1. Figma에서 화면 프레임, 구성 요소, 상태, 인터랙션을 확인한다.
2. `src/shared/ui`와 기존 화면에 같은 역할의 컴포넌트가 있는지 확인한다.
3. 토큰과 공용 UI를 우선 사용해 화면을 조합한다.
4. 화면 전용 구조와 데이터 조합은 FSD 레이어 규칙에 맞는 `views`, `widgets`, `features`, `entities`에 둔다.
5. 360px, 390px, 430px에서 UI와 주요 동작을 확인한다.

새로운 색상, spacing, radius, typography 값이 필요하면 화면에 임의 값을 추가하지 않습니다. 먼저 `src/app/globals.css`에 semantic 또는 component token이 필요한지 검토하고, [디자인 시스템](./design-system.md)을 함께 갱신합니다.

## 화면 레이아웃

### 기준 폭과 여백

- 모바일 디자인 기준 프레임은 `390 x 844 CSS px`다.
- 일반 본문은 좌우 `16px` 여백을 기본으로 한다. 390px 기준의 콘텐츠 폭은 `358px`이지만, CSS 폭을 `358px`로 고정하지 않는다.
- 공통 컨테이너에는 `.mobile-page`, 내부 본문에는 필요할 때 `.mobile-page--padded`를 사용한다.
- 화면 본문은 360px, 390px, 430px에서 의도되지 않은 가로 오버플로 없이 fluid하게 줄어들어야 한다. 가로 레일과 칩 목록의 내부 스크롤은 예외다.
- full-bleed 이미지, 배경, 구분선은 화면 전체 폭을 사용할 수 있다. 내부 텍스트와 조작 요소는 Figma가 별도 지시하지 않는 한 공통 여백 안에 둔다.
- 긴 제목, 가격, 옵션명, 안내 문구는 줄바꿈 또는 말줄임의 의도를 Figma와 명세에서 확인한다. 임의로 고정 높이로 잘라내지 않는다.

### 시스템 상태바와 안전영역

- Figma 모바일 프레임에 포함된 시간, 통신 상태, 홈 인디케이터는 OS 시스템 UI다. 웹 화면에서 아이콘이나 고정 여백으로 복제하지 않는다.
- 시스템 상태바가 포함된 Figma의 절대 `y` 좌표를 CSS 값으로 그대로 사용하지 않는다. 헤더와 제목, 제목과 선택 영역처럼 **앱 콘텐츠끼리의 상대 간격**을 기준으로 구현한다.
- 피그마에 상태바 높이가 포함되어 있으면 화면 요소의 절대 좌표를 비교할 때 상태바 영역을 제외한 콘텐츠 원점 기준으로 환산한다. 예를 들어 Figma의 상태바가 `47px`이고 선택 영역이 `y=279px`이면, 웹 콘텐츠 기준 비교값은 `y=232px`다.
- 노치나 전체화면 PWA처럼 웹 콘텐츠가 안전영역과 겹칠 수 있는 화면만 `padding-top: env(safe-area-inset-top)`과 `padding-bottom: env(safe-area-inset-bottom)`을 사용한다. `47px`처럼 특정 기기 값을 하드코딩하지 않는다.
- 데스크톱 Chrome의 기기 에뮬레이션에서는 안전영역 값이 `0px`일 수 있다. 이 경우 Figma의 시스템 상태바를 빈 공간으로 만들지 않는다.

### 높이와 스크롤

- 화면의 고정 높이를 `844px`로 강제하지 않는다. 콘텐츠가 길면 문서가 자연스럽게 세로 스크롤되어야 한다.
- 이미지 비율, 헤더, 카드처럼 Figma에서 명확히 고정된 영역만 고정 높이 또는 `aspect-ratio`를 사용한다.
- 하단 고정 CTA, bottom sheet, dialog가 있으면 본문에 그 높이만큼 하단 여백을 확보해 콘텐츠와 겹치지 않게 한다.
- `100vh` 대신 모바일 브라우저 주소창 변화를 반영하는 `100dvh`를 사용한다.
- 가로 스크롤이 필요한 상품 레일과 칩 목록은 해당 목록 요소에만 `overflow-x-auto`를 적용한다. 하단 내비게이션이나 페이지 전체를 감싸는 컨테이너에는 적용하지 않는다.

### 간격과 구분

- spacing은 `0, 4, 8, 12, 16, 20, 24, 32, 40px` 토큰 단위를 우선 사용한다.
- 같은 계층의 카드, 목록 행, 버튼은 동일한 gap과 padding을 사용한다.
- 섹션 사이의 분리는 여백 또는 divider 중 Figma의 표현을 따른다. 단순히 공간을 만들기 위해 임의의 두꺼운 border를 추가하지 않는다.
- radius는 `sm(8px)`, `md(12px)`, `lg(16px)` 중 역할에 맞는 값을 사용한다.

## 타이포그래피와 색상

### 타이포그래피

- 전역 폰트는 Pretendard이며, 크기와 줄높이는 `text-title-*`, `text-body-*`, `text-label-*` utility를 우선 사용한다.
- 제목, 본문, 보조 정보의 위계를 폰트 크기만으로 만들지 않는다. 디자인 시스템의 weight와 색상 역할을 함께 사용한다.
- 주요 제목은 `h1`, 섹션 제목은 `h2`처럼 문서 구조에 맞는 semantic element를 사용한다. 글자 크기 때문에 heading 태그를 선택하지 않는다.
- Figma의 줄바꿈은 390px 기준 확인 자료다. 더 좁은 폭에서 자연스럽게 바뀌도록 폭을 고정하지 않는다.

### 색상과 와이어프레임

- 페이지 배경, 텍스트, 버튼, border, overlay에는 `bg-background`, `text-foreground`, `text-muted-foreground`, `bg-primary`, `border-border` 같은 semantic token을 사용한다.
- `#FFCD55` 같은 primitive 색상값이나 `bg-white`, `text-white`를 화면 코드에 직접 작성하지 않는다.
- low-fi 단계의 이미지, 카드, skeleton placeholder는 회색 표현을 유지할 수 있다. placeholder 이외의 실제 UI 역할에는 semantic token을 사용한다.
- 선택, 오류, 소비기한, 판매 불가 같은 상태를 색상만으로 전달하지 않는다. 텍스트, 아이콘, 배지, 테두리 등 추가 단서를 제공한다.

## 공통 패턴

### 헤더와 진행 상태

- 뒤로가기, 닫기, 공유 같은 아이콘 버튼은 아이콘의 실제 크기와 별개로 충분한 터치 영역을 둔다.
- 뒤로가기는 가능한 경우 브라우저 히스토리 기반으로 처리하고, 히스토리가 없을 때만 화면별 fallback 경로로 이동한다.
- 온보딩의 진행 바와 `현재 단계/전체 단계` 표기는 같은 진행 상태를 나타내므로 함께 갱신한다.
- 헤더는 페이지별로 `fixed`를 남용하지 않는다. 스크롤 중에도 항상 필요한 조작일 때만 sticky 또는 fixed를 선택한다.

### 선택 카드와 필터

- 단일 선택은 native radio group으로 구현한다.
- 복수 선택은 native checkbox를 우선 사용한다. 선택 카드 자체가 독립적인 토글 행동이면 native `button`에 `aria-pressed`를 사용한다.
- `aria-pressed`를 일반 `div`나 비대화형 카드에 단독으로 추가하지 않는다. 키보드 조작과 대화형 의미를 함께 제공해야 한다.
- 선택/미선택 상태는 Figma의 배경, border, 아이콘, 텍스트 규칙을 함께 적용한다.
- 2열 선택 카드처럼 반복되는 grid는 화면 폭에 맞춰 줄어들어야 하며, 카드 내부 텍스트가 잘리지 않아야 한다.
- 비활성 항목은 클릭 불가 상태와 그 이유를 시각적·접근성 측면에서 함께 전달한다.

### 하단 CTA와 내비게이션

- 하단 CTA는 화면의 핵심 다음 행동 하나를 우선한다. 복수 버튼은 주·보조 행동의 위계를 명확히 둔다.
- `sticky bottom-0` 또는 `fixed` CTA는 safe area와 본문 하단 padding을 함께 설계한다.
- 하단 내비게이션은 페이지 스크롤과 독립적으로 접근 가능해야 한다. 부모의 `overflow-hidden` 때문에 sticky 동작이 깨지지 않게 한다.
- 버튼은 default, focus-visible, disabled, loading 상태를 필요한 범위에서 제공한다. 요청 중 중복 실행을 막아야 하면 `disabled`를 사용한다.

### 목록과 가로 레일

- 카드 목록은 카드 크기, 카드 간 gap, 양끝 여백을 한 화면 안에서 일관되게 유지한다.
- 가로 레일은 첫 카드가 본문 시작선에 맞고, 마지막 카드가 잘릴 수 있음을 의도적으로 보여줄 때만 bleed 처리를 사용한다.
- 카드 전체가 상세 이동 대상이면 링크로 만들고, 이동 대상이 없는 목업 카드는 클릭 가능한 것처럼 보이게 만들지 않는다.
- 가격, 판매 불가, 재고 등 구매 판단에 필요한 정보는 스크린 리더에서도 확인할 수 있어야 한다.

### Dialog와 Bottom Sheet

- 확인이 필요한 파괴적 행동에만 확인 dialog를 사용한다. 취소·닫기·확인의 의미를 분명히 구분한다.
- dialog와 bottom sheet를 열면 포커스를 내부로 이동하고, Tab 및 Shift+Tab 포커스가 내부를 벗어나지 않게 한다.
- Escape는 취소 또는 닫기 동작으로 처리하고, 닫을 때는 열기 트리거로 포커스를 되돌린다.
- 스크롤 가능한 sheet는 제목과 핵심 CTA가 가려지지 않도록 최대 높이와 내부 scroll 영역을 둔다.

## 상태와 예외

- 데이터 화면은 `loading`, `content`, `empty`, `error`, `unauthorized`를 구분한다.
- 최초 조회에는 skeleton을 사용하고, skeleton 컨테이너에 `aria-busy`를 제공한다. 장식용 placeholder는 `aria-hidden`으로 숨긴다.
- 빈 상태에는 이유를 설명하는 문구와 화면별 우선 CTA를 제공한다.
- 오류 상태에는 재시도 가능한 경우 Retry CTA를 제공한다. 실제 재시도 방식은 API 계약과 화면 요구사항에 맞춘다.
- 이미지가 없거나 로드에 실패한 상태, 긴 텍스트, 데이터 누락은 각 화면 구현 전에 표시 규칙을 정한다.
- 와이어프레임에 실제 데이터 연동이 아직 없으면, 목업 데이터도 도메인 구조와 화면 상태를 재현할 수 있게 만든다.

## 접근성 최소 기준

- 아이콘만 있는 버튼에는 목적을 설명하는 `aria-label`을 제공한다.
- 폼 입력에는 연결된 label을 제공하고, placeholder를 label 대용으로 사용하지 않는다.
- 키보드 포커스 표시를 제거하지 않는다. 제거가 필요하면 같은 수준 이상의 `focus-visible` 스타일을 제공한다.
- 빈 달력 칸이나 장식 요소처럼 동작하지 않는 요소를 button으로 렌더링하지 않는다.
- 링크는 실제 이동이 있을 때만 사용한다. 클릭 결과가 없는 요소는 링크나 버튼처럼 보이게 하지 않는다.
- 사용자에게 전달되는 상태 변화는 필요에 따라 `aria-live` 또는 명확한 상태 문구로 알린다.

## FSD와 공용화 기준

- `src/app`에는 라우팅과 전역 설정만 둔다.
- 화면 조합은 `src/views`, 재사용 가능한 큰 블록은 `src/widgets`, 사용자 행동은 `src/features`, 도메인 모델과 단위 UI는 `src/entities`, 범용 UI와 유틸은 `src/shared`에 둔다.
- 하나의 화면에서만 쓰이고 화면 문맥이 필요한 코드는 성급하게 `shared`로 올리지 않는다.
- 버튼, 입력, dialog, sheet, card처럼 여러 화면에서 역할과 상태가 같은 UI만 `src/shared/ui` 공용화를 검토한다.
- 새 컴포넌트를 만들기 전 기존 `shared/ui`와 유사 화면 구현을 먼저 확인한다.

## 구현 전·후 체크리스트

### 구현 전

- [ ] Figma 링크와 대상 node를 이슈 또는 PR에 남겼다.
- [ ] 화면의 기본, 선택, disabled, loading, empty, error 상태 범위와 인증 필요 화면의 unauthorized 상태를 확인했다.
- [ ] 기존 공용 컴포넌트와 토큰 사용 가능 여부를 확인했다.
- [ ] 하단 CTA, dialog, bottom sheet, 가로 레일의 스크롤·포커스 영향을 확인했다.

### 구현 후

- [ ] 360px, 390px, 430px에서 페이지의 의도되지 않은 가로 오버플로와 콘텐츠 잘림이 없다. Figma에서 정의한 가로 레일·칩 목록의 내부 스크롤과 마지막 카드의 의도된 잘림은 예외로 확인했다.
- [ ] 390px 기준 Figma와 padding, gap, radius, typography, 정렬을 비교했다.
- [ ] Figma 시스템 상태바를 CSS에 중복 구현하지 않았고, 절대 좌표가 아닌 콘텐츠 기준 상대 간격으로 비교했다.
- [ ] 버튼, 링크, 입력, 선택 UI를 키보드로 조작할 수 있고 포커스가 보인다.
- [ ] dialog 또는 bottom sheet의 포커스 이동, Tab 순환, Escape, 포커스 복귀를 확인했다.
- [ ] placeholder를 제외한 UI에 primitive 색상이나 임의 typography 값을 추가하지 않았다.
- [ ] `npm run check`, `npm run test`, `npm run build`를 실행했다.

## 변경 원칙

- 이 문서는 공통 구현 기준만 다룬다. 특정 화면의 고정 높이, 카드 폭, 화면 전용 문구는 해당 Figma와 이슈에 둔다.
- 공통 패턴이 두 개 이상의 화면에서 반복되고 역할·상태·동작이 같을 때만 component token 또는 `shared/ui` 공용화를 제안한다.
- Figma와 가이드가 충돌하거나 새로운 상태가 필요하면 임의로 해석하지 말고 디자인·기획과 확인한 뒤, 결정 내용을 이 문서 또는 디자인 시스템에 반영한다.
